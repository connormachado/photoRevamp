# backend/ — non-obvious wiring

> Loaded automatically when working under `backend/`. Root-level rules (never commit,
> the ffmpeg-is-bundled convention, how to run `make test`) live in `/CLAUDE.md` and
> still apply. Frontend-side preview behaviour is in
> `photo-search/src/components/motion-review/CLAUDE.md`.

- **A `video_id` is a path component, so it is validated at every path-building site, not once at the route.** `_proposal_path` / `_review_path` / `_draft_path` / `_preview_path` all run `safe_paths.safe_id_component` (which *rejects* path syntax rather than stripping it — a sanitised-but-different id would silently address the wrong file). The reason it can't be a single route-level check: `proposals/`, `reviews/` and `drafts/` are **sibling** dirs, so a `../`-laden id made the guard-read and the subsequent write resolve to the *same* file outside the tree — `save_draft` became an arbitrary overwrite of any valid-JSON file and `_clear_draft` an arbitrary `unlink`. Verified by removing the guard and watching a sentinel file outside the tree get overwritten. **Only the sentinel/unit tests in `TestVideoIdTraversal` actually guard this** — re-confirmed by fault injection: with `safe_id_component` gutted, the parametrized `*_refuses_a_traversing_id` route sweeps all stayed GREEN, because a traversing id 404s on the missing proposal long before it reaches the guard. Don't read those sweeps as protection. `/full` and `/thumbnail` take a raw `?path=` and are contained by `resolve_within_roots` (resolves *before* comparing, so a symlink out of the library fails too); roots default to the Photos library + `photo_db`, overridable with `PHOTO_MEMORY_ROOTS`. Refusals are **403**, distinct from a 404, and never reveal whether the file exists.
- **`server.py` is no longer open to the world, and two env vars control that.** `CORS` is scoped to `localhost:5173` (override: `PHOTO_MEMORY_ORIGINS`) and `debug` is off unless `PHOTO_MEMORY_DEBUG=1` — a bare `CORS(app)` plus no auth meant any page the user browsed could call these routes and read the response, which is what turned a path bug into a drive-by. Routes coerce input through `_json_body` / `_int_param`: **malformed input returns 4xx, never 500**, and `n` is clamped to `MAX_RESULTS` before it reaches `collection.query`. Keep that property when adding a route — `tests/test_input_validation.py` sweeps every route for it.

- **`reclaimed_bytes` in `stats.json` is derived — never assign it.** It is the sum of `reclaimed_breakdown`, whose three slots are the only writable things: `photos_exact` (a real size read out of Photos at reveal time), `photos_estimated` (count-only culls valued at `stats.AVG_PHOTO_BYTES`), and `climb_cutter`. Every writer in `stats.py` ends with `_recompute_total`. The split exists because `set_climb_cutter_bytes` is an **absolute** set of `sum(per_video.values())` — with one shared scalar, the next verdict silently wiped the photo bytes. The authoritative per-video video record is still `photo_db/motion_review/savings.json`; `_apply_savings` writes there, then mirrors the total into the `climb_cutter` slot alone. Legacy files carrying only the scalar migrate on read by seeding it into `climb_cutter` (it was that field's sole writer), so the headline survives the upgrade. Both the review room (`GET /motion-review/savings`, video bytes only) and now the main page's DeleteCounter (`/stats`, all three) read this — keep them in sync.
- **`/reveal` is also the only moment a photo's real size is knowable, so it returns one.** `cleanup.photo_size_bytes` asks Photos for `size of media item id` in its **own** osascript call, deliberately not folded into the spotlight script (that script has an unconfirmed intermittent failure and must stay byte-identical). Do not substitute the Chroma `size_kb` metadata: we index *derivatives*, measured at ~60–90 KB against 1.8–6.4 MB originals — off by ~50×. Every failure returns 0 and must never turn a successful reveal into an error.
- **`render_plan` picks its ffmpeg strategy from the plan.** If every piece is a straight copy (speed 1, no filters) it uses the concat demuxer with inpoint/outpoint — the drop-only path, verified byte-identical to the pre-registry renderer. Any piece needing a transform switches the whole render to one `-filter_complex` graph (per-piece `trim`/`setpts` + `atrim`/`asetpts`/`atempo`, then `concat`), because the concat demuxer cannot vary playback rate per entry. That path then needs a second stream-copy pass (`_strip_display_matrix`) — see the rotation invariant below. `render_segments` is now a thin wrapper over it.
- **Video re-encode invariants — four ways to silently corrupt an export.** All four were hit and fixed once; don't reintroduce them. (1) **Rotation needs no flag.** On re-encode ffmpeg autorotates, baking the source's display matrix into the pixels — a 1920x1080 iPhone source carrying a -90° matrix comes out a true 1080x1920 portrait file. Adding `-metadata:s:v:0 rotate=` is a no-op in ffmpeg 7 (re-verified) and would double-rotate already-upright footage if it ever started working. (1b) **…but the `-filter_complex` path ALSO copies the matrix onto the output**, so the already-upright pixels get rotated a second time and the clip lands sideways in Photos. The concat-demuxer path does not, which is why drop-only exports were always fine and this only surfaced with the first transforming boundary type. `export_video._strip_display_matrix` fixes it with a stream-copy pass using `-display_rotation 0` on the input — the only flag that clears it (`-metadata:s:v:0 rotate=0`, `-map_metadata:s:v:0 -1` and `-noautorotate` were all tried and all leave it). That remux **drops `creation_time`** (GPS survives), so the date/GPS tags are stamped on the remux rather than the encode. (2) **iPhone `.MOV` carries streams this build cannot decode** — a 4-channel `apac` spatial-audio track plus several `mebx` data tracks. Map explicitly (`-map 0:v:0 -map 0:a:0?`); letting ffmpeg auto-map fails the encode outright. (3) **Date and GPS must be re-stamped**, they do not survive a re-encode on their own: `-metadata creation_time=` (prefer the source's `com.apple.quicktime.creationdate`, which is local wall-clock with offset — the timestamp Photos files by) and the ISO-6709 location string.
- **Two independent mechanisms date an exported clip, and both are kept.** The `creation_time` container tag written during the render, and `set date of media item id ...` via AppleScript after import. The second was expected to be read-only but is settable on current macOS (verified); they agree. Keep both — the container tag needs no automation permission and survives an AppleScript vocabulary change.
- **The preview proxy is versioned by filename, and is NOT the export path.**
  `motion_review.PREVIEW_SUFFIX` (`_h264_v2.mp4`) is the cache-buster: the mtime check
  can't notice that the *encode settings* changed, so bump the suffix whenever they do
  and stale files get unlinked on next open. The proxy caps its long side at 1280
  (`PREVIEW_SCALE`) because the panels are ~350px wide — this is a display-only
  downscale and never touches an export, which always re-reads the original. That `-vf`
  scale was verified NOT to copy the source display matrix (portrait stays upright with
  no rotation flag), unlike the export's `-filter_complex` path — see the rotation
  invariant above, and don't assume the two behave alike.
  **Generating it must stay serialised per video.** The three review panels share one
  `/motion-review/source` URL, so a cache miss fires three concurrent transcodes; they
  used to share one temp path, interleave, and publish a file whose moov atom held
  another writer's bytes — which the mtime check then served forever, so the clip never
  played again. `_proxy_lock` (one lock per video_id) plus a per-call temp name and a
  `_proxy_is_playable` check before `os.replace` close it. Reproduced deterministically
  with three concurrent `source_h264_path` calls; keep all three guards.
- **A source file's rotation flag can disagree with its own pixels, and nothing in the metadata reveals it.** Diagnosed on `IMG_8883.mov`: coded frame is upright landscape, yet the container carries `displaymatrix: rotation of -90`, so every conformant player turns it sideways — **including Photos**, whose own derivative for that clip renders portrait. Another clip from the same phone carries a byte-identical `tkhd` matrix and genuinely needs the rotation. iOS guesses orientation at record time and can guess wrong. So a sideways preview is not automatically our bug: extract a frame with `-noautorotate` and *look* before touching the rotation code, and don't try to auto-detect this — only a manual per-video override can fix it.
- **An upload's path IS its identity.** `video_upload.py` parks files at `uploads/<content-hash>/<name>` and `video_id` is md5-of-absolute-path, so moving or renaming an uploaded file orphans its proposal, review, draft and preview proxy. The content hash (not the filename) is the dedupe key, which is what keeps a re-picked clip from landing a second few-hundred-MB copy on an already-full disk.
- **`queue_removal` imports `motion_review`, so the two places that need it back import it lazily.** `list_queue` does a function-body `import queue_removal` to compute the wire's `owned` field — that is a cycle break, not sloppiness; don't hoist it. For the same reason `queue_removal._uploads_dir()` *derives* `MOTION_DIR / "uploads"` instead of importing `video_upload.UPLOADS_DIR` (which would also drag numpy/ffmpeg in behind it), and deriving it from `mr.MOTION_DIR` is what makes it follow the `tmp_motion_db` fixture's redirect. That duplicated constant is held in step by `test_the_uploads_dir_matches_the_upload_routes`.
- **`/reveal` takes a `file_id`, but reveals by `apple_uuid`.** Photos are indexed from the derivatives cache, whose paths Photos.app doesn't know. The route looks the row up by `id`, pulls `apple_uuid` from metadata, and hands that to `cleanup.reveal_in_photos`, which runs `spotlight media item id` via AppleScript. Never try to reveal by filename or path.
- **The UMAP reducer was fit on a 2,000-photo sample** (`photo_db/models/layout_meta.json`, `count_at_fit: 2000`, Jul 3) and has not been refit. All ~49.6k photos carry `x`/`y` because `compute_layout.py incremental` projects new rows onto that existing reducer. The map's *structure* therefore comes from a 2k subset — the likely reason the layout looks off. A full refit is `compute_layout.py` full-fit mode.
- **Cluster labels are Agglomerative, not density-based.** `compute_layout.py` uses `sklearn.cluster.AgglomerativeClustering` at fixed k (`broad_k=12`, `fine_k=60`), writing `cluster_id_broad`/`cluster_id_fine` back to ChromaDB. There is no HDBSCAN in this project.
- **Photos' importer doesn't reliably read the ffmpeg-embedded date/GPS container tags on their own — verified live via `osascript`.** `export_video.import_to_photos` force-sets both afterward via AppleScript (`set date of media item ...`, `set location of media item ... to {lat, lon}`); the container tags are kept too since they're free, but are not sufficient alone. `_try_set_item_date` builds its target date by mutating a `current date` object's year/month/day in that order — mutating `month` while `day` still holds *today's* day-of-month overflows into the next month whenever today's day exceeds the target month's length (e.g. exporting a Feb 11 clip while running on the 31st silently landed on March 11th). Fixed by setting `day` to 1 first. `_try_set_item_location` mirrors the pattern for GPS, parsing `{lat, lon}` out of the ISO-6709 string (altitude dropped — Photos' `location` property doesn't take one).
- **A saved draft always wins over the review's stored regions in `list_queue()`, regardless of prior verdict.** Re-editing an already-approved/exported video and saving a new draft is a normal workflow, not an edge case — don't gate draft lookup on `verdict != "approve"` again, it silently discards edits on any video that's ever been exported once. `export_to_photos` clears the draft the moment a real export succeeds, which is what lets the review's regions take back over.
